# Move the 1050 Ti to the R520, retire the 750 Ti

**Why:** the 3200g has hard-locked **three times in 18 hours**, with intervals shortening
(6 days -> 8h31m -> 5h30m). Every software capture path came back empty:

    journal          ends mid-routine-entry, no error, all three times
    NMI watchdog     never fired -- so the CPU is not spinning, it is stopping
    hardlockup_panic set to 1 before lockup #3; no panic, no auto-reboot
    pstore           0 entries after lockup #3 (efi_pstore registered and working)

That combination is platform-level, not kernel-software, and the passed-through consumer GPU
is the only variable that changed when the box started crashing. The card also refuses
function-level reset (`error writing '1' to .../reset: Inappropriate ioctl`), which is a known
source of host hangs.

**The destination is demonstrably good at this.** R520 hypervisor uptime is **6 weeks 22h**
with a GPU passed through to VM 101 the whole time.

---

## What we learned while planning

**The 750 Ti has been doing nothing for three weeks.** `karakeep-ollama-embed` runs
`mxbai-embed-large` at **100% CPU**:

    WARN "NVIDIA driver too old" device="GTX 750 Ti" compute=5.0
         driver=550 required_driver="570 or newer"

Everything about that setup looks correct -- card passed through, container has
DeviceRequests, `nvidia-smi` works inside it, compute 5.0 meets Ollama's stated minimum.
It is a *driver version* check, unrelated to the hardware, and it produced one WARN line
on 2026-07-30 and no symptom since.

**So retiring the 750 Ti costs nothing**, and moving the embed model onto GPU needs a driver
upgrade to 570+ on VM 101 **regardless of which card is in the slot** -- 1050 Ti is Pascal
6.1, but the check is on driver version, not compute capability. Treat that as a separate,
optional follow-up.

## VM 101 vs the 3200g VM

| | 3200g VM 100 | R520 VM 101 |
|---|---|---|
| cores | 4 | **12** |
| RAM | 12 GB | **30 GB** (18 free) |
| media | CIFS (oplock + permission trouble, documented in its own compose) | **NFS, already mounted, writable** |
| driver / CUDA | 550.163.01 / 12.4 | **identical** -- no regression |
| docker GPU | CDI (dual-spec gotcha) | CDI already configured |
| host stability | 3 lockups / 18 h | 6 weeks uptime |

VRAM is not a constraint: Whisper turbo int8 was measured at **~1 GB of 4 GB** during
generation, and the embed model is 684 MB even if it later moves to GPU.

## !! User-facing outage !!

**R520 must be powered down for the physical swap, and VM 100 (OMV) serves the entire media
pool.** Plex and Jellyfin both lose their library for the duration. VM 101 additionally runs
~43 containers including qBittorrent, saltcorn, karakeep, salyut and the hub broker.

Per standing practice: **post a Discord maintenance announcement as the fasc bot before and
after.**

## Sequence

### Before powering anything down
- [ ] Announce the outage (Discord, fasc bot)
- [ ] Stop the DubTitlerr container on the 3200g and leave it stopped.
      The pipeline has NO locking -- two workers on one library race on `<stem>.muxtmp.mkv`
      and across protocols. This is the single most important step.
      `ssh 3200g-docker 'cd /home/claude/docker-stacks/dubtitle-builder && docker compose stop'`
- [ ] Copy the config off the 3200g (glossaries, cache, anime_order, season_priority):
      `rsync -a 3200g-docker:/home/claude/docker-data/dubtitle-config/ vm101:~/dubtitle-config/`
- [ ] Note v4 progress so it can be confirmed unchanged afterwards.

### Physical
- [ ] Shut down R520 VM 101 and VM 100 gracefully, then the hypervisor.
- [ ] Pull the 750 Ti from R520, seat the 1050 Ti in the same slot.
      Both are slot-powered (60 W / 75 W, no aux connector) -- no PSU change.
      **Verify the card physically fits the 2U chassis before committing.**
- [ ] Pull the 1050 Ti from the 3200g.
- [ ] On the 3200g: remove the GPU from VM 100 or it will fail to start --
      `ssh 3200g 'qm set 100 --delete hostpci0'`

### After power-on
- [ ] Confirm the 1050 Ti enumerates at the same address: `lspci -nn | grep -i nvidia`
      (VM 101 has `hostpci0: 09:00`; if the address changed, update it)
- [ ] `ssh vm101 'nvidia-smi'` -> expect GTX 1050 Ti, driver 550.163.01
- [ ] Confirm the 43 containers came back: `ssh vm101 'docker ps -q | wc -l'`
- [ ] Confirm media: `ls "/mnt/r520-media-full/Anime Library" | wc -l` -> 93

### Bring DubTitlerr up on VM 101
- [ ] Copy the repo tree: `rsync -a ~/claude/DubTitlerr/ vm101:~/DubTitlerr/`
- [ ] Build on the target box (standing permission):
      `cd ~/DubTitlerr && docker build -f Dockerfile.builder --build-arg WHISPER_MODEL=large-v3-turbo -t dubtitle-builder:latest .`
- [ ] New compose, adapted from the 3200g one. Changes:
      - `ANIME_ROOT` / volume -> bind `/mnt/r520-media-full/Anime Library` (NFS, **no CIFS
        driver_opts at all** -- the whole oplock/permission section goes away)
      - keep `REPAIR_LLAMACPP_URL: http://192.168.1.209:8090/...` (nanbeige on fasc, unchanged)
      - keep `WATCHSTATE_URL` / `WATCHSTATE_API_KEY`, `PLEX_*`, `WATCH_QUEUE_WINDOW_DAYS: 90`,
        `WATCH_QUEUE_PIN: One Pace`, `ACQUIRE_TIMEOUT: 10800`
      - `restart: unless-stopped`, nvidia CDI device reservation
- [ ] Start it, confirm the watch queue writes and GENERATE resumes.
- [ ] Confirm v4 count matches what it was before the move -- the `.done` stamps are the
      proof no work was lost.
- [ ] Announce the outage over (Discord, fasc bot)

## Afterwards
- The 3200g becomes a GPU-less Docker host. Still useful; nothing else on it needed the GPU.
- If it keeps locking up **without** the GPU, the card was innocent and the box has a
  different fault -- that is itself the cleanest possible test.
- Optional: upgrade VM 101's driver to 570+ so `mxbai-embed-large` finally runs on GPU.
