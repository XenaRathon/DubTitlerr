# Move Whisper/DubTitlerr to the R520: 1050 Ti into VM 102, retire the 750 Ti

**Status:** planned, not started
**Why now:** the 3200g has hard-locked **three times in 18 hours**, intervals shortening.

---

## 1. The evidence for moving

    lockup 1   Aug 21 21:51:46   after ~6 days up
    lockup 2   Aug 22 06:57:12   after 8h31m
    lockup 3   Aug 22 15:00:00   after 5h30m

Every software capture path came back empty, including ones armed specifically for lockup 3:

    journal            ends mid-routine-entry, no error, all three times
    NMI watchdog       never fired -- so the CPU is not spinning, it is stopping
    hardlockup_panic   set to 1 before #3; no panic and no auto-reboot followed
    efi_pstore         registered and working; 0 entries after #3

An NMI is non-maskable and exists precisely to catch a spinning CPU. Its silence rules out the
common kernel-software lockup and points at the platform: a machine check that halts a core, a
PCIe bus hang, power delivery, or firmware. The passed-through consumer GPU is the only
variable that changed when the box began crashing, and that card **refuses function-level
reset** (`error writing '1' to .../reset: Inappropriate ioctl for device`) -- a known cause of
host hangs.

Further software instrumentation will not catch this. Removing the variable will.

**The destination is demonstrably good at exactly this workload shape:** R520's hypervisor has
**42 days 23 h uptime** with a GPU passed through to a VM the entire time.

---

## 2. Two findings that changed the plan

### The 750 Ti has been idle for three weeks

`karakeep-ollama-embed` runs `mxbai-embed-large` at **100% CPU**:

    WARN "NVIDIA driver too old" device="GTX 750 Ti" compute=5.0
         driver=550 required_driver="570 or newer"

Card passed through, container has DeviceRequests, `nvidia-smi` works inside it, compute 5.0
meets Ollama's stated minimum -- every check a person would run comes back green, and it has
been on CPU since 2026-07-30 behind a single WARN line.

So **retiring it costs nothing.** Note the check is on *driver version*, not compute
capability, so the 1050 Ti (Pascal 6.1) would be rejected too. Putting the embed model on GPU
needs a driver upgrade to 570+ regardless of which card is in the slot -- separate, optional.

### LXC was considered and rejected

LXC GPU access is bind-mounting `/dev/nvidia*`, which requires the NVIDIA driver on the
**hypervisor**. Today the host has no driver at all; `09:00.0` is bound to `vfio-pci` via
`/etc/modprobe.d/vfio.conf`.

Going LXC would mean installing an out-of-tree DKMS module on the one machine in this story
that has never crashed, rebuilding it on every Proxmox kernel update, and promoting a GPU
driver fault from "contained in a VM" to "host problem". The usual payoff is GPU *sharing* --
which is moot, because the embed model cannot use this GPU anyway (see above).

The vfio suspicion does not transfer either: R520 has run vfio GPU passthrough for six weeks
without incident. The lockups are the 3200g's platform, not vfio as a mechanism.

**Use VM 102, with PCI passthrough, exactly as VM 101 does today.**

## 3. Target: VM 102, resized

VM 102 (`ollama-deepthink`) is stopped and idle. It was sized to hold a large model in RAM;
Whisper does not need that -- the model lives in VRAM.

**Measured on the 3200g mid-transcription** (GPU at 80%, so real load):

    dubtitle-builder container   1.33 GiB
    whole VM                     3.42 GB of 11.96 GB
    GPU VRAM                     1085 MiB of 4096

### RAM: 32768 -> 8192 MB. Not optional -- the box is overcommitted.

    R520 physical         62 GB
    running now           51 GB   (VM100 8 + VM101 31 + LXC104 8 + LXC105 4)
    VM 102 as configured  32 GB
                          -----
                          83 GB   -- 21 GB over

At 8 GB: `51 + 8 = 59 GB of 62`, leaving ~3 GB for the hypervisor, and 8 GB is still 2.3x the
measured peak.

**NUMA gotcha -- memory is declared twice.** VM 102 has:

    numa: 1
    numa0: cpus=0-3,memory=16384,hostnodes=0,policy=bind
    numa1: cpus=4-7,memory=16384,hostnodes=1,policy=bind

Setting `--memory 8192` while those still read 16384+16384 leaves the two disagreeing and
Proxmox refuses to start the VM. The pinning is a leftover from holding a model in RAM, where
socket-local memory mattered; for a 1.3 GB workload it is pure liability. Drop it:

    qm set 102 --memory 8192 --delete numa0 --delete numa1 --numa 0

### CPU: 8 vCPU, verified available

    physical           32 logical (2 x Xeon E5-2450, 8c/16t each)
    running allocation 22 vCPU  (VM100 4 + VM101 12 + LXC104 4 + LXC105 2)
    VM 102 adds        8  ->  30 of 32
    current load       4.44 on 32 CPUs (~14%)

Comfortable, and CPU overcommit is benign in a way RAM overcommit is not.

**Caveat:** the E5-2450 is 2.1 GHz against the 3200G's 3.6 GHz, so per-core work (ffmpeg audio
extraction, any CT2 CPU fallback) is slower -- offset by 8 cores instead of 4. Expect
comparable or slightly better throughput, not a large win.

### Disk: 100 GB, keep

The image is a few GB and all sidecars live on NFS beside the media. Also present:
`unused0: local-lvm:vm-102-disk-0`, an orphaned disk worth reclaiming while we are in there.

## 6. Sequence

### Before powering anything down
- [ ] Announce the outage (Discord, fasc bot)
- [ ] **Stop the DubTitlerr container on the 3200g and leave it stopped.** The pipeline has NO
      locking -- two workers on one library race on `<stem>.muxtmp.mkv`, and across protocols
      they do not even share a coherent metadata view. This is the single most important step.
      `ssh 3200g-docker 'cd /home/claude/docker-stacks/dubtitle-builder && docker compose stop'`
- [ ] Record the v4 count so it can be confirmed unchanged afterwards:
      `docker exec dubtitle-builder python3 -c "import json,glob; print(sum(1 for p in glob.glob('/media/Anime Library/One Pace/Season */*.dubtitles.done') if json.load(open(p)).get('version')==4))"`
- [ ] Copy the config off the 3200g -- glossaries, the 855 KB acquire cache, anime_order,
      season_priority: `rsync -a 3200g-docker:/home/claude/docker-data/dubtitle-config/ <staging>/`

### Resize VM 102 (can be done now, it is stopped)
- [ ] `qm set 102 --memory 8192 --delete numa0 --delete numa1 --numa 0`
- [ ] `qm set 102 --delete unused0` (reclaims the orphaned disk)
- [ ] Boot it once **without** the GPU and verify: NFS media mount, docker + nvidia container
      toolkit, CUDA runtime. It was an Ollama VM so the driver may already be present.

### Physical
- [ ] Shut down VM 101 and VM 100 gracefully, then the hypervisor.
- [ ] Swap: 750 Ti out of R520, 1050 Ti in the same slot.
      Both are slot-powered (60 W / 75 W, no aux connector) -- no PSU change.
      **Verify the card physically fits the 2U chassis before committing.**
- [ ] Pull the 1050 Ti from the 3200g.
- [ ] On the 3200g, remove the GPU from its VM or it will not start:
      `ssh 3200g 'qm set 100 --delete hostpci0'`

### After power-on
- [ ] `lspci -nn | grep -i nvidia` -- confirm the 1050 Ti enumerates at **09:00**. If the
      address moved, update the hostpci line accordingly.
- [ ] Remove the now-dead passthrough from VM 101: `qm set 101 --delete hostpci0`
      (it was only feeding a container that runs on CPU anyway)
- [ ] Attach to VM 102: `qm set 102 --hostpci0 09:00,pcie=1`
- [ ] Start VM 102; `nvidia-smi` should report GTX 1050 Ti.
- [ ] Confirm VM 101's 43 containers came back and media is serving.

### Bring DubTitlerr up on VM 102
- [ ] `rsync -a ~/claude/DubTitlerr/ vm102:~/DubTitlerr/`
- [ ] Restore the config directory from staging.
- [ ] Build on the target box (standing permission):
      `docker build -f Dockerfile.builder --build-arg WHISPER_MODEL=large-v3-turbo -t dubtitle-builder:latest .`
- [ ] New compose, adapted from the 3200g's. Changes:
      - media: bind-mount the **NFS** path. **The entire CIFS `driver_opts` block goes away** --
        with it the oplock/permission trouble documented in that compose.
      - keep `REPAIR_LLAMACPP_URL: http://192.168.1.209:8090/...` (nanbeige on fasc, unchanged)
      - keep `WATCHSTATE_URL`/`WATCHSTATE_API_KEY`, `PLEX_*`, `WATCH_QUEUE_WINDOW_DAYS: 90`,
        `WATCH_QUEUE_PIN: One Pace`, `ACQUIRE_TIMEOUT: 10800`, `VERIFY_TIMEOUT: 1200`
      - `restart: unless-stopped`; nvidia CDI device reservation
      - `onboot: 1` on the VM -- the 3200g needed this added by hand after a crash
- [ ] Start; confirm the watch queue writes 15 shows and GENERATE resumes.
- [ ] **Confirm the v4 count matches the pre-move number** -- the `.done` stamps are the proof
      no work was lost.
- [ ] Announce the outage over (Discord, fasc bot)

## 7. Afterwards

- The 3200g becomes a GPU-less Docker host. Nothing else on it used the GPU.
- **If it keeps locking up without the GPU, the card was innocent and the box has a different
  fault.** That is the cleanest available test and costs nothing to observe.
- Optional: upgrade VM 102's driver to 570+ so the embed model could also run on GPU -- but
  only if the embed workload moves there too.
- The `hardlockup_panic`/`panic=10` sysctls on the 3200g are worth keeping either way.
