# Repository-wide adversarial review — 2026-09-01

## Scope and method

This review covers the repository's production surface, not only the recent handoff:

- all 24 top-level Python modules;
- all four shell scripts, including `shell/lib.sh`;
- both Dockerfiles and the container supervisor;
- pipeline stages from audio selection/transcription through punctuation, reflow,
  hallucination gating, repair, glossary mining/acquisition/verification, signs merge,
  muxing, Plex refresh, review, and recovery tools;
- checked-in data/configuration and the 34 test modules;
- repository-wide tests, Python compilation, shell syntax, and Ruff.

Commands run:

```text
pytest -q
python -m compileall -q -- *.py tools tests
sh -n container_run.sh gen_loop.sh merge_pass.sh shell/lib.sh
ruff check .
```

Result: **all checks passed**. The test suite is valuable but heavily unit-oriented; it
cannot prove real ffmpeg/mkvmerge behavior, network failures, mounted-filesystem semantics,
GPU/model compatibility, or concurrent HTTP behavior.

## Executive summary

The codebase has unusually strong defensive intent: atomic writes are common, media paths are
usually allow-listed, the review server has token authentication by default, LLM failures
fall back conservatively, and many historical regressions have dedicated tests.

The main risk is not ordinary algorithmic failure. It is **cross-stage state ambiguity**:
multiple independent sidecars, stamps, caches, environment variables, and shell loops jointly
represent whether an episode is complete. Several paths can therefore produce a plausible
success signal while a stage failed, used a different configuration, or produced output that
cannot be validated later.

Priority labels:

- **P0:** can corrupt/overwrite media, expose privileged mutation, or cause sustained outage.
- **P1:** can silently ship materially wrong/incomplete output or strand operational state.
- **P2:** correctness/availability weakness with bounded or recoverable impact.
- **P3:** maintainability, performance, or testability debt.

## Findings

### F1 — P0/P1: production container runs a root-owned HTTP mutation service on all interfaces

**Evidence:** `Dockerfile.builder` runs `/app/container_run.sh`; the supervisor starts
`review_server.py`; `review_server.py` defaults `REVIEW_BIND=0.0.0.0`; the review service can
rewrite subtitle sidecars, remove stamps, and trigger re-muxing. The README publishes port 8842.

Authentication is generated by default, which is good, but the threat model remains broad:
anyone who obtains the token can request root-owned media mutations, and the default bind makes
LAN exposure easy. The server's GET routes are unauthenticated and disclose episode names,
paths, queue contents, model output, and potentially sensitive media metadata. The POST parser
reads a declared body before authentication, and the threaded server has no hard global worker
limit at the socket layer. A slow client can hold connections while the body is being read.

**Impact:** a leaked token permits destructive/reversible media operations; a LAN attacker can
exhaust review-server workers; unauthenticated readers can inventory the media tree. The merge
and generate loops are separate, so this is not automatically whole-container compromise, but
it is a privileged service with a larger exposure than the UI description suggests.

**Recommendation:** bind to loopback by default and require explicit opt-in for LAN exposure;
make GET routes token-gated or redact filesystem paths; set socket/read deadlines and a bounded
request semaphore; run the review server as a non-root process or isolate its privileged helper;
add CSRF protection if browser access is expected beyond a trusted LAN.

### F2 — P1: stage completion is not an atomic transaction and shell orchestration hides failures

**Evidence:** `merge_pass.sh` invokes `repair.py`, `dub_signs_merge.py`, and `mux.py` without
checking each Python exit code. `container_run.sh` deliberately logs and continues after a
merge-pass failure. The mux stamp is written by `common.write_stamp`, while sidecar cleanup
happens afterward in `mux.py`. Review/write-back also changes the SRT, ASS, and stamp in separate
operations.

The implementation is restart-oriented, but there is no durable transaction record spanning
“repair ran,” “sign merge succeeded,” “mux verification passed,” and “sidecars removed.” A
process crash or a swallowed nonzero exit can leave combinations such as a current-looking
stamp, stale sidecars, a dialogue-only SRT, or a generated file whose later stage never ran.
The newer optional `stages` field improves observability only when the caller reaches the
stamp-writing path; it does not make the transitions atomic.

**Impact:** materially wrong or incomplete subtitles can look complete; operators may not know
which stage to retry. Recovery often exists, but it depends on recognizing the intermediate
state correctly.

**Recommendation:** make each stage return structured status; fail the episode transaction
closed; write a durable stage manifest before stamping; only stamp after all required stages
and verification pass; make cleanup conditional on successful replacement; add crash-injection
integration tests around every boundary.

### F3 — P1: configuration is read independently in many modules, with known semantic drift

**Evidence:** environment variables are read directly throughout Python and shell code. The
repository itself documents examples such as `DUB_SUFFIX` being honored by some paths but
hardcoded by others, `REQUIRE_ENG` being forced in `gen_loop.sh`, and model/version settings
not being encoded into all validity checks. `MERGE_ROOTS`, `MUX_ROOTS`, `ANIME_ROOT`,
`MEDIA_ROOT`, `OUTPUT_ROOT`, `GLOSSARY_DIR`, `DECISIONS_DIR`, and `GLOSSARY_FILE` are not one
validated runtime configuration object.

This creates split-brain behavior: a path can be generated under one root/suffix and consumed
under another; a bare checkout and the container can select different models; a value can be
accepted by one stage while ignored by another. The pipeline's most important idempotency
checks are therefore partly dependent on operator knowledge rather than machine validation.

**Impact:** skipped work, duplicate work, wrong file selection, or stale output without a
single obvious exception.

**Recommendation:** centralize runtime configuration and validate it once at startup; print a
redacted resolved manifest; eliminate unsupported aliases and hardcoded overrides; include all
decoder-affecting inputs (model, compute type, beam, audio filter, prompt) in the transcribe
identity.

### F4 — P1: model and decoder identity is not fully represented by the transcribe stamp

**Evidence:** `common.read_words()` validates `transcribe_version`; `stale_tiers()` validates
numeric tier versions and file size/mtime. The persisted words document includes `model` and
`initial_prompt`, but the validity path does not compare them. `generate.py` explicitly notes
that changing `WHISPER_MODEL` without bumping `TRANSCRIBE_VERSION` is undetected. Similar
concerns apply to `COMPUTE_TYPE`, beam settings, audio filters, and other decoder-affecting
options.

**Impact:** a downstream operator can rebuild with a different decoder while existing v4
words/stamps remain accepted. The library becomes a mixture of transcript-generation regimes,
with no automatic migration or warning. This is particularly dangerous because the resulting
subtitles remain syntactically valid and therefore pass downstream stages.

**Recommendation:** derive a canonical decoder configuration hash and record it in words and
stamps; reject mismatches as stale; provide an explicit migration mode when an intentional
model change is desired.

### F5 — P1: reference extraction and LLM failures collapse into “no reference/no answer”

**Evidence:** `common.extract_sub()` discards subprocess status/stderr and infers success from
output-file existence/size. `_load_stream_events()` returns `[]` on extraction or parse errors.
`common.llm_chat()` catches broad exceptions and returns an empty string. Repair and punctuation
then continue with conservative fallbacks, which is safer than blindly applying a bad model
answer but does not distinguish “clean/no reference” from “infrastructure failed.”

**Impact:** a broken ffmpeg extraction, malformed subtitle, unavailable LLM, or timeout can
silently reduce anchoring and coverage. Unanchored repair is specifically the least verifiable
class; the output may be accepted as a normal run while quality regresses.

**Recommendation:** return typed outcomes (`ok`, `missing`, `parse_error`, `timeout`,
`transport_error`); record them in QC and stage manifests; make “infrastructure failure”
visible and optionally block or retry instead of treating it as ordinary absence.

### F6 — P1: review decisions are split across text-pair stores and per-episode queue flags

**Evidence:** `decisions.save()` and `unresolved.resolve_many()` are separate writes. The review
server saves the decision first, then clears queue entries. The CLI can mark a repair-applied
entry resolved without recording a corresponding decision. Decision identity is normalized
text-pair based, while queue entries are indexed by file position.

**Impact:** partial writes can leave stale UI state; CLI and web workflows can have different
semantics; changed proposals for the same original produce competing review entries. The mux
path is designed to consult durable decisions, so many failures recover, but the system does
not have one authoritative, reconciled state machine.

**Recommendation:** make decisions authoritative and derive queue visibility from them, or add
an explicit reconciliation pass; use stable IDs/content hashes instead of mutable numeric
indices; ensure every review command records an auditable decision or explicitly records a
non-decision dismissal.

### F7 — P1: review/apply can produce a dialogue-only merged track after transient sign failure

**Evidence:** `review_apply.py` rewrites the SRT and drops ASS/stamp before the next merge pass.
`merge_pass.sh` then runs repair, signs merge, and mux. `dub_signs_merge.py` can return no-signs,
empty, or build-error while leaving an SRT for mux. This is a sensible fallback for episodes
that genuinely have no signs, but it is not equivalent for an episode that previously had a
successful signs merge.

**Impact:** a transient extraction/build failure can publish an apparently successful mux with
only dialogue in the generated track. Source sign tracks may remain in the video, so this is
not necessarily irreversible loss, but the operator's requested combined track is degraded and
there is no durable “signs merge was required but failed” state tied to the stamp.

**Recommendation:** persist whether the prior/current episode had usable signs; distinguish
“No signs exist” from “sign extraction failed”; do not mark the combined-track requirement
complete on the latter; retry or preserve the previous output until replacement verification
passes.

### F8 — P2: `OUTPUT_ROOT` path redirection is not proven safe across all readers/writers

**Evidence:** `common.out_for()` redirects only paths beginning with `MEDIA_ROOT`, while many
callers use raw `stem + suffix` paths and comments explicitly acknowledge mixed raw/output
path assumptions. `review_apply.py`, `mux.py`, `unresolved.py`, and `review_server.py` each
operate on related sidecars, but not every operation visibly applies the same redirection
policy.

**Impact:** with `OUTPUT_ROOT` enabled, one stage can write a sidecar to the output branch
while another looks beside source media, producing duplicate work, stale detection failures,
or apparently missing decisions. This may be harmless in the default empty configuration but is
a high-risk deployment option precisely because it changes storage semantics.

**Recommendation:** represent a stem as a source path plus a derived artifact path; route every
sidecar operation through one path mapper; add an integration test with distinct source/output
trees and a full pipeline lifecycle.

### F9 — P2: shell path handling and environment interpolation are fragile

**Evidence:** `gen_loop.sh` uses shell expansion for `WATCH_QUEUE_PIN` inside an optional command
fragment; `merge_pass.sh` constructs a regex from directory names through `extras_grep_pattern`;
`find | grep | sed` pipelines are used for media discovery. Names containing regex metacharacters,
newlines, leading dashes, or unusual Unicode can be misclassified or transformed. The scripts
also rely on `set -u`/`set -e` exceptions and command substitution behavior that is difficult to
reason about across shells.

**Impact:** an unusual show/directory name can be skipped, matched incorrectly, or cause a loop
to abort. Media libraries commonly contain punctuation and bracketed release metadata, so this
is not purely theoretical.

**Recommendation:** use Python for discovery and argument passing; use null-delimited `find -print0`
where shell remains; quote data as data rather than constructing command fragments; test hostile
filenames.

### F10 — P2: network integrations lack strong endpoint and response validation

**Evidence:** `watch_queue.py`, `plex_refresh.py`, glossary verification/acquisition, and the
shared LLM client call operator-configured URLs. The LLM client parses URL schemes but does not
appear to restrict destinations or enforce TLS policy beyond what the URL requests. WatchState
and Plex responses are parsed from JSON/XML/text with varying validation. Secrets such as Plex
and WatchState tokens are placed in request URLs or logs may expose operational details through
errors.

**Impact:** a misconfigured or compromised endpoint can receive media-derived prompts and
secrets; malformed successful responses can be interpreted as empty/stale data, changing queue
or glossary behavior. The service is self-hosted, so SSRF risk is primarily operator/config
and local-network risk rather than an unauthenticated remote exploit.

**Recommendation:** require explicit endpoint allowlists or document the trust boundary; keep
credentials in headers rather than query strings; validate response schemas and content types;
redact URLs/errors; use HTTPS by default for non-local endpoints.

### F11 — P2: data files and runtime assets are not consistently validated or pinned

**Evidence:** both Dockerfiles leave apt and pip dependencies broadly/unpinned; the builder
conditionally installs `webrtcvad` and continues after failure; the Docker build downloads a
Whisper model at build time based on a mutable model name. Runtime data files have fallback
behavior when missing, including blocklists, extras, wordlists, and glossaries.

**Impact:** two builds from the same source can differ; a dependency/model update can change
transcription, parsing, or security behavior; a missing data file can silently switch policy.
The fallback philosophy helps development but can conceal a production image that is missing an
expected asset.

**Recommendation:** pin/lock production dependencies and base image digests where practical;
fail builds when required assets are absent; verify model checksums; distinguish development
fallbacks from production behavior and emit a startup manifest.

### F12 — P2/P3: broad exception handling makes failures difficult to classify and recover

**Evidence:** many production paths use `except Exception` and return `[]`, `None`, `""`, or a
status string. This is intentional in several observability paths, but the same convention is
used around ffprobe, subtitle parsing, LLM calls, glossary acquisition, Plex refresh, and
pipeline loops.

**Impact:** the caller often cannot tell whether a feature found nothing, was disabled, timed
out, or crashed. This compounds F2, F3, F5, and F11 and makes metrics optimistic: a complete
run can have large hidden failure volume.

**Recommendation:** narrow exception classes where possible; attach typed failure reasons;
record them in QC/stage manifests; reserve broad catches for process boundaries and log with
stable error codes.

### F13 — P3: test coverage does not exercise the real integration contract

**Evidence:** the full suite passes, but most tests monkeypatch subprocess/network calls and
invoke handlers directly. There are no evident end-to-end tests covering a real media fixture
through generate → repair → signs merge → mux → restart. There are no socket-level slow-body,
concurrency, or browser tests; no real mounted-filesystem/output-root lifecycle; no crash
injection between stamp and sidecar removal; and no model identity migration test.

**Impact:** unit behavior can remain green while deployment semantics regress. The repository's
history shows that many serious bugs were cross-module contract failures, exactly the class least
covered by isolated tests.

**Recommendation:** add a small checked-in media fixture and an integration harness with fake
ffmpeg/LLM/Plex services; test restart/crash boundaries, hostile paths, alternate roots, and
real HTTP framing; keep expensive GPU tests optional but run them before image release.

### F14 — P3: operational documentation and repository state are easy to confuse

**Evidence:** README, specs, plans, review documents, `.procoder` artifacts, and checked-in
runtime data coexist. Several documents describe historical or superseded behavior, while
comments frequently contain measured live-library facts that are not reproducible from the
checkout. The repository also contains generated artifacts/cache directories in the working
area and a deprecated Dockerfile with a different runtime contract.

**Impact:** operators can follow stale instructions, reviewers can mistake historical analysis
for current guarantees, and a clean checkout may not resemble the production image or data
state.

**Recommendation:** label historical documents and current operational docs distinctly; add a
single supported deployment guide; add a release manifest showing exactly what is in the image;
exclude generated caches/artifacts from distribution and CI where appropriate.

## Prioritized remediation

1. **Constrain and deprivilege the review service** (F1).
2. **Make stage status durable and failure-aware before stamping** (F2, F5, F12).
3. **Unify/validate configuration and decoder identity** (F3, F4).
4. **Make signs-required output fail closed on transient extraction/build failures** (F7).
5. **Reconcile review decisions and eliminate CLI/web semantic divergence** (F6).
6. **Test `OUTPUT_ROOT`, hostile filenames, and real socket/media lifecycle** (F8, F9, F13).
7. **Harden endpoint/secret handling and production dependency/data reproducibility** (F10, F11).
8. **Separate current operational documentation from historical review artifacts** (F14).

## Rebuttal — arguing against every finding

This section intentionally argues the strongest defensible case against each finding. It does
not erase the findings; it identifies where severity depends on deployment assumptions,
missing evidence, or an unstated contract.

### F1 rebuttal — privileged review server exposure

The service is explicitly self-hosted, LAN-oriented, and designed for one trusted operator.
The default-generated token, constant-time comparison, path allow-list, and separate process
loop substantially reduce the practical threat. GET disclosure is limited to data already on
the operator's own media disk, and a user who can obtain the token or write the container's
config is already close to administrator-level access. The slow-drip issue affects the review
convenience service, not the generator or merge loop, and the supervisor restarts it.

Therefore F1 should not automatically block the pipeline. It is a defense-in-depth and
availability issue whose severity is P2 in a trusted LAN deployment, rising to P0 only when the
port is forwarded, a reverse proxy is shared, or the config/media volume is accessible to
untrusted users. Loopback-by-default is safer, but explicit LAN binding is a defensible product
choice for the documented workflow.

### F2 rebuttal — non-atomic stage completion

Media pipelines necessarily cross process and filesystem boundaries; a single transaction
cannot atomically cover ffmpeg, model inference, subtitle files, and a video replacement.
Atomic temp-file replacement, verification, stamps, restart loops, stale-sidecar parking, and
separate stage metadata already provide practical crash recovery. A crash between stamp and
cleanup is detectable and generally recoverable, while requiring every stage to fail closed
could strand episodes indefinitely on optional sign or LLM failures.

The shell's “continue” behavior is also intentional: one bad episode or optional service must
not stop a library-wide sweep. F2 is thus a robustness improvement, not proof that the current
pipeline routinely publishes corrupt media. The right fix may be better stage status and
reconciliation rather than a strict all-or-nothing transaction.

### F3 rebuttal — configuration drift

A centralized configuration schema can become a second stale source of truth. The current
project is a flat script collection with environment variables intentionally read close to the
stage that owns them; this keeps tools standalone and avoids a framework. Several apparent
mismatches are documented, tested, or deliberate (`REQUIRE_ENG=1`, separate merge/generate
roots, optional `OUTPUT_ROOT`). Operators who use the supported container path receive sane
defaults.

Thus F3 is primarily maintainability debt. A startup log and removal of known dead aliases may
capture most of its value at much lower cost than a new configuration subsystem.

### F4 rebuttal — decoder identity

The repository knowingly uses two-tier versioning and records the model/prompt in words for
auditability. The maintainer's production library was generated with the current decoder, and
changing decoder behavior is an explicit operator action that can legitimately require a manual
version bump. Automatically hashing every performance-affecting option can trigger expensive
unwanted re-transcription and make harmless implementation changes operationally disruptive.

The downstream old-default scenario is real but conditional and already called out in source
comments. It is better classified as a migration/documentation gap than an active defect in the
maintainer's deployment.

### F5 rebuttal — silent extraction/LLM failures

The conservative fallback is deliberate safety engineering. If a reference cannot be extracted
or the LLM is unavailable, leaving ASR text unchanged is safer than applying an unanchored or
partially parsed correction. The unresolved queue and QC counters provide an observability path,
and broad catches prevent one malformed episode from killing a sweep.

Typed outcomes would improve operations, but the finding does not show that a failed reference
causes wrong text by itself; it usually causes less automation. F5 is therefore a visibility
and quality-coverage problem, not automatically a data-corruption problem.

### F6 rebuttal — split review state

The decision store is intentionally authoritative for pipeline behavior, while queue flags are
worklist metadata. Keeping those concerns separate permits show-wide decisions without rewriting
many episode files and makes partial queue-write failure recoverable. Numeric indices are only
used after server-side re-resolution of the known episode, and duplicate entries are largely
idempotent because decisions are keyed on normalized text pairs.

The CLI asymmetry is a real usability edge, but it does not prove incorrect media output in the
normal web workflow. F6 should be narrowed to reconciliation and audit consistency rather than
called a general correctness failure.

### F7 rebuttal — dialogue-only result after sign failure

The fallback is correct for genuine dialogue-only releases, and the original sign streams are
normally retained in the mux input. A failed signs merge does not necessarily destroy signs; it
can leave the source tracks available separately. The next sweep can retry, and the pipeline
already favors keeping usable dialogue over blocking an episode forever because an optional
presentation layer failed.

The strongest surviving point is the absence of a durable distinction between “no signs” and
“sign extraction failed.” That is an operational quality signal, not demonstrated irreversible
media loss.

### F8 rebuttal — OUTPUT_ROOT

`OUTPUT_ROOT` is an advanced option, not the default, and the comments explicitly acknowledge
that it relies on the output branch being visible through the same mergerfs/pool view. Under
that supported storage model, raw and redirected paths can resolve to the same apparent media
paths. A full abstraction would be cleaner but may be unnecessary for the actual deployment.

F8 should remain a targeted integration-test requirement until a concrete divergent-tree failure
is reproduced.

### F9 rebuttal — shell path handling

The supported library naming convention is ordinary show/episode paths, and the current tests
cover many title-normalization cases. POSIX shell quoting is present in the main argument paths;
the regex helper is intentionally derived from a controlled data file rather than arbitrary user
input. Most unusual filename cases are benign skips rather than destructive writes.

Still, hostile filename tests are cheap. F9 is best treated as robustness debt unless a specific
name reproduces a wrong episode selection or shell injection.

### F10 rebuttal — network trust boundaries

All network endpoints are operator-configured local services in the intended deployment, so
allowlisting private hosts would add friction without protecting against an operator who can
already change environment variables. Plex query-token use may be dictated by its API, and the
LLM endpoint is deliberately configurable across Ollama and llama.cpp deployments.

The meaningful residual is secret redaction and schema validation, not a likely unauthenticated
SSRF. F10 should be P2 hardening, not a release blocker.

### F11 rebuttal — unpinned dependencies and fallbacks

The project intentionally avoids apt pinning because Debian package versions rotate and rigid
pins break rebuilds. `uv.lock` covers the Python development environment, while the provided
builder image is anchored to a dated subgen base image and installs optional analytics support
without making generation depend on it. Fallbacks keep bare checkouts and older images usable.

Reproducibility would improve with digest/checksum controls, but the current policy is a
conscious availability trade-off. The finding is valid as supply-chain/reproducibility debt,
not proof that current builds are unsafe.

### F12 rebuttal — broad exception handling

A long-running media batch should isolate failures per episode. Returning safe sentinel values
and continuing is intentional at process boundaries, and many catches log the exception and
write QC/unresolved evidence. Narrowing every catch can turn a recoverable bad file into a
library-wide outage.

The better compromise is stable error categories at boundaries while retaining broad containment
in the top-level loops. F12 overlaps F2 and F5 and should not be counted as a separate high-
severity defect for every `except Exception` occurrence.

### F13 rebuttal — integration test gap

The repository has extensive unit/property coverage and deliberately mocks expensive or
environment-specific tools so development remains fast and deterministic. Real GPU/media tests
are hardware- and fixture-sensitive, and a fake integration harness can itself diverge from
ffmpeg/mkvmerge behavior.

The absence of end-to-end coverage is still a meaningful confidence limit, but passing 100% of
the suite plus syntax/static checks is evidence that local logic is stable. F13 is a test-plan
recommendation, not evidence of a production bug.

### F14 rebuttal — documentation/repository hygiene

Historical reviews and specs are valuable project memory, and the README clearly identifies the
recommended builder image and deprecated Dockerfile. Keeping design artifacts near code supports
traceability for a rapidly evolving solo project. Generated caches appear to be local working
state rather than necessarily shipped artifacts.

The risk is navigational rather than functional. A single current deployment guide would help,
but F14 should remain P3.

## Final assessment after rebuttal

The rebuttal lowers the severity of several findings but does not eliminate the central risk:
state is represented by multiple files and processes with weakly typed failure boundaries. The
highest-confidence, least assumption-dependent actions are:

1. add socket/read deadlines and explicit exposure controls to the review server;
2. make stage outcomes and transient sign/reference failures visible in durable status;
3. encode decoder/config identity into reuse checks or make the migration contract explicit;
4. add integration tests for crash boundaries, alternate roots, hostile names, and real HTTP.

The repository is not shown to be universally unsafe, and the full suite is green. It is also
not justified to treat green unit tests as proof that the deployed media lifecycle is correct.
